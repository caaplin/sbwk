About

Sleepy Bot sits between your users and your server. Every request passes through the edge. The edge detects anomalies, dispatches them to the agent, and the agent reasons about dependencies and code — then either proposes a fix or wakes a human.

The stack

   ┌──────────┐    ┌──────────────┐    ┌─────────┐
   │  CLIENT  │───▶│  MIDDLEWARE  │───▶│ SERVER  │
   └──────────┘    │    (edge)    │    └─────────┘
                   └──────┬───────┘
                          │ anomaly
                          ▼
                   ┌──────────────┐    ┌──────────────┐
                   │ AGENT CORE   │───▶│  CONNECTOR   │
                   │ (reasoning)  │    │  (read-only) │
                   └──────┬───────┘    └──────────────┘
                          │
                          ▼
                   ┌──────────────┐   deliberate?   ┌──────────────┐
                   │ LIQUID d1    │─── no ─────────▶│   ENGINEER   │
                   │  (triage)    │                 │  (hand-off)  │
                   └──────┬───────┘                 └──────────────┘
                          │ technical
                          ▼
                   ┌──────────────┐
                   │  GROQ AI     │  diagnosis + diffs
                   └──────────────┘

Each incident is triaged by Liquid AI's d1 decision model first: billing/sales questions and very frustrated reporters go straight to a human, everything technical goes to Groq. No Liquid key configured? Every incident defaults to "call Groq AI". If a provider call fails, the Agent tab shows it in red and the incident still gets analysed.

What each tab does

  • Requests — live view of everything passing through the edge. Rows with a left bar were flagged as anomalies and dispatched to the agent. Click a row to see the request ID, upstream, client IP and a response sample.
  • Config — the whole stack in one form: server target, external services, codebase link, safety limits, and the monitoring switch. The AI section at the bottom configures the Liquid router and lets you A/B test Groq prompts against a synthetic incident.
  • Config → AI — pick a prompt profile (balanced, concise, diff_first, strict_json, sre_checklist), edit the system prompt or user template, then "Run test incident" to see exactly what the AI returns. Warnings appear inline when something will be stored but not monitored, or sent over plaintext.
  • About — this page.

What gets pushed where

  • TARGET_URL → middleware (/_sbwk/config) so the edge re-points immediately.
  • External services → connector (/connector/config), only for HTTP-scheme endpoints of kind auth, database or external_api. Non-HTTP endpoints (mongodb+srv:, postgres:, …) are stored but the connector does not monitor them.
  • REPO_URL + commits → agent-core (/config) for commit correlation.
  • Safety limits + monitoring switch → agent-core (/config).

What this page cannot verify

  • It cannot prove the edge container is actually routing traffic — only that the control plane can reach the target from its own network.
  • It cannot check that the API token you provided is read-only. It can check that the auth endpoint answered, but any HTTP response (including 401 and 403) counts as "reachable".
  • It cannot monitor a MongoDB, Postgres or Redis endpoint. Those are DNS-checked only.
  • The "auto-rollback within 60 seconds" promise lives in agent-core, not here.
